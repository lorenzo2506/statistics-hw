HMWK 2 – From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives

1. The pipeline

Mnemonic → (BIP-39) → Seed → (BIP-32 / BIP-44) → Private key → (secp256k1) → Public key → (Keccak-256) → Ethereum address → (EIP-55) → Checksummed address

Each arrow is a different kind of operation, with a different purpose.

2. Role of each standard or primitive

BIP-39 (mnemonic and seed). Encodes random entropy (128–256 bits) as a list of 12–24 words from a fixed 2048-word list; the last bits are a checksum (first bits of SHA-256 of the entropy). The words are turned into a 512-bit seed with PBKDF2-HMAC-SHA512 (2048 iterations, optional passphrase). Purpose: human-friendly backup of the wallet secret.

BIP-32 (HD key derivation). From one seed it derives a whole tree of keys: HMAC-SHA512 with the key "Bitcoin seed" gives a master private key and a chain code; child keys are derived deterministically from parent key, chain code and an index. Purpose: one backup, unlimited keys.

BIP-44 (derivation paths). Fixes a standard layout of the tree: m / 44' / coin_type' / account' / change / address_index. For Ethereum, coin_type = 60, so the first account is m/44'/60'/0'/0/0. Purpose: interoperability, so the same mnemonic gives the same addresses in MetaMask, Rabby, Ledger, etc.

secp256k1 (public-key cryptography). The elliptic curve y² = x³ + 7 over a 256-bit prime field with a standard base point G. Public key Q = k·G, where k is the private key. Going from k to Q is easy (double-and-add); going back is the Elliptic Curve Discrete Logarithm Problem, believed infeasible. It is also the basis of ECDSA signatures used to sign transactions. This is exactly what HMWK 1 shows on a toy curve.

Keccak-256 (hash). The uncompressed public key (64 bytes, x‖y, without the 0x04 prefix) is hashed with Keccak-256; the Ethereum address is the last 20 bytes (40 hex characters) of the digest.

EIP-55 (checksum). Take the lowercase hex address, hash its ASCII text with Keccak-256, and capitalise each letter whose corresponding hash nibble is ≥ 8. The result is a mixed-case address that detects typing mistakes (probability of an undetected random error about 1/215 per address) while remaining fully backward-compatible.

3. Key concepts to distinguish

  • Key generation vs key derivation. Generation creates fresh secret randomness (the entropy behind the mnemonic). Derivation is deterministic: the same input always gives the same keys (BIP-32/44, and PBKDF2 for the seed). No new randomness is added after the first step.
  • Public-key cryptography. Asymmetric key pair with a one-way relation (k → Q) enabling signatures without sharing secrets. Security rests on a hard mathematical problem (ECDLP).
  • Hashing. A fixed-size fingerprint of arbitrary data, deterministic, one-way, collision-resistant, with avalanche effect. Not reversible and not encryption.
  • Checksums. Small redundant data to detect accidental errors (BIP-39 last bits, EIP-55 capitalisation). They are not secret and not designed against attackers.
  • Encoding. Reversible change of representation with no secrecy (hex, the word list, mixed-case letters). Anyone can decode it.

4. Statistical properties

  • Entropy and uniformity. Security depends on the initial entropy being uniformly random: 256 bits give 2256 possible secrets.
  • Hashes and KDFs (SHA-256, PBKDF2, HMAC-SHA512, Keccak-256). Designed so that outputs look uniform and each input bit flip changes about 50% of output bits (avalanche). Similar inputs give unrelated outputs.
  • secp256k1. Outputs look statistically uniform, but there is no avalanche: (k+1)·G = k·G + G, and k·G and (n−k)·G share the same x. As we saw in HMWK 1, uniformity-like behaviour is not what protects it; ECDLP hardness is.
  • EIP-55. The capitalisation pattern behaves like random bits derived from a hash, which is why a single wrong character is detected with probability ≈ 1 − 2−15 on average.

5. Chronological context

  • 1977 – RSA: first widely used public-key cryptosystem.
  • 2001 – SHA-2 (incl. SHA-512): standardised by NIST; used in BIP-39/BIP-32 (PBKDF2, HMAC-SHA512).
  • 2012 – BIP-32: hierarchical deterministic wallets.
  • 2013 – BIP-39: mnemonic code.
  • 2014 – BIP-44: multi-account derivation paths.
  • 2015 – SHA-3: standardised by NIST, based on Keccak. Ethereum launched in 2015 with the original Keccak submission.
  • 2016 – EIP-55: mixed-case checksum addresses.

The wallet standards therefore come from the Bitcoin world (2012–2014) and were adopted by Ethereum; the choice of secp256k1 was inherited from Bitcoin.

6. SHA-2/SHA-512 vs Keccak/SHA-3

SHA-2 uses the Merkle–Damgård construction with a compression function; SHA-3/Keccak uses a completely different design, the sponge construction (absorb and squeeze on a permutation state). They are both cryptographic hash families but are structurally unrelated, and SHA-3 was chosen by NIST as a backup with a different design.

Ethereum's "Keccak-256" is the original Keccak as it was before standardisation. NIST's SHA3-256 changed the padding/domain-separation byte (0x06 instead of Keccak's 0x01), so the two functions give different outputs for the same input. Ethereum uses the pre-standard version, so an address computed with SHA3-256 would be wrong.

7. Why several different techniques?

No single algorithm can do everything, because each task needs different properties:

  • BIP-39 / BIP-32 / BIP-44 → key management and derivation: backup, many keys from one secret, compatibility across wallets.
  • secp256k1 → public/private key relationship and signatures: lets anyone verify a transaction without learning the secret.
  • Keccak-256 → hashing: compresses the public key to a short, uniform-looking 20-byte identifier and hides the public key until the first spend.
  • EIP-55 → checksum / error detection: protects users from typos without changing the address format.

Separation also improves security and flexibility: a weakness in one component does not automatically break the others, and components can be replaced independently (for example, a different hash or curve).
